# Design

## Context

Ver `proposal.md` - Why/What Changes para a motivação completa. Resumo do estado atual relevante para as decisões abaixo:

- **`frontend/` (produção)**: React 19 + Vite + TS, `react-router-dom` v7, `react-i18next` (namespaces `comum/mapa/relacoes/admin/sessoes/linhaTempo`, pt-BR + en), `react-zoom-pan-pinch`, `react-markdown` + `rehype-sanitize`. Auth real por cookie de sessão; `EditModeContext` resolve `canEdit`/`isDono` via `GET /api/c/{slug}/admin/session`. Build: `frontend/Dockerfile` (`node:22-alpine` → `npm ci` → `vite build` → `nginx:1.27-alpine` serve), consumido pelo serviço `web` de `docker-compose.yml` — SPA estático, sem runtime Node em produção.
- **`frontend-next/`**: protótipo React+Vite, `HashRouter`, dados 100% mock, zero chamada de API, sem i18n, Modo GM é toggle local. Confirmado sem valor de reaproveitamento (ver proposal.md).
- **`paper-parchment-pages-main`** (base visual nova): template Lovable **TanStack Start** (SSR via Nitro, target cloudflare) + **TanStack Router** (file-based, `src/routes/`) + **TanStack Query** (instanciado, sem uso real) + React 19 + **Tailwind v4** (CSS-first, `@theme inline`, paleta OKLCH própria) + **shadcn/ui "new-york"** sobre Radix (~34 componentes instalados, maioria não usada pelas páginas) + `lucide-react` + **bun**. 5 rotas (`/`, `/relacoes`, `/rota`, `/sessoes`, `/cronologia`) visual e interativamente completas, mas 100% sobre `src/lib/codex-data.ts` (mock estático), zero integração de rede, zero i18n, Modo "Mestre" só visual.
- **Backend (`backend/app/`)**: FastAPI + SQLModel, ~70 endpoints sob `/api/auth/*`, `/api/campanhas/*`, `/api/admin/*` (super-admin), `/api/c/{slug}/...` (config, locais, npcs, personagens, vínculos, arcos, sessões, eventos, itens, waypoints, route-segments, routes/plan, grupo, media, uploads, export, admin/session). Isolamento multi-tenant por banco SQLite físico separado por campanha (não por `campaign_id` em linha). Auth 100% cookie de sessão + membership (`require_session_user`/`require_membro`/`require_dono`), `require_admin` separado para super-admin — o README do projeto cita HTTP Basic Auth, mas isso está obsoleto e não deve ser usado como referência de contrato. Regra de visibilidade central `is_visivel_para_jogador()`. Nenhuma mudança de contrato é proposta aqui.

## Goals / Non-Goals

**Goals:**
- Entregar `frontend-v2/` com o design system de `paper-parchment-pages-main` — e **somente** ele, sem nenhum resquício visual de `frontend/`/`frontend-next/` (ver Decision 9) — sobre a mesma stack de tecnologia de aplicação que o projeto já usa (`react-router-dom`, client HTTP próprio, `react-i18next`, `react-markdown`/`rehype-sanitize`, `react-zoom-pan-pinch`, Decision 1), e com paridade funcional completa com `frontend/`.
- Adaptar o template à stack de build/deploy já usada pelo projeto (SPA + nginx + Docker + npm), sem introduzir um runtime de servidor novo em produção.
- Não regredir nenhuma garantia já especificada (i18n, auth real, isolamento multi-tenant, regras de visibilidade, Markdown sanitizado, cálculo de rota real, 8 tipos de vínculo).
- Permitir que `frontend-v2/` seja construído e validado inteiramente em paralelo, sem risco para `frontend/` em produção até o cutover explícito.

**Non-Goals:**
- Mudar qualquer contrato de API do backend — se a implementação revelar uma lacuna real, isso abre uma change OpenSpec separada.
- Redesenhar a informação/fluxo de qualquer tela além do necessário para herdar o design do template e cobrir a paridade — este não é um redesign de produto, é uma migração de base de código e visual.
- Resolver a lacuna de "sem endpoint de catálogo de módulos" no backend (`modulos_ativos` continua hardcoded no cliente, como já é hoje em `frontend/`).
- Expor a lista pública de Itens (`GET /api/c/{slug}/itens`) como tela nova de jogador — essa capacidade já existe no backend sem consumidor hoje; criar UI para ela é uma extensão de produto, não uma paridade. **Decidido**: fica fora do escopo desta change; será proposta como uma OpenSpec separada (nova capability, não uma tarefa de `frontend-v2`).

## Decisions

### 1. Do template, adotar só o design visual — a stack de aplicação continua sendo a de `frontend/`
**Decisão**: `frontend-v2/` remove inteiramente o harness de aplicação do template — `@tanstack/react-start` (SSR/Nitro), `@tanstack/react-router` e `@tanstack/react-query` — e usa, em vez disso, exatamente as mesmas bibliotecas de aplicação que `frontend/` já usa hoje: `react-router-dom` para roteamento, um client HTTP próprio + hooks (mesmo padrão de `frontend/src/api/`) para dados, sem lib de cache de servidor, `react-i18next` para i18n, `react-markdown` + `rehype-sanitize` para conteúdo rico, `react-zoom-pan-pinch` para pan/zoom do mapa (substituindo o pan/zoom caseiro — `onPointerDown/Move/Up`/`onWheel` manual com transform CSS — de `WorldMap.tsx` no template). Build vira **SPA estático puro** (Vite), consequência direta de não usar TanStack Start. Do template, o que de fato é adotado é só a camada visual: Tailwind v4, `shadcn/ui`/Radix, paleta OKLCH, tipografia (ver Decision 9).
**Por quê**: pedido explícito do usuário — "manter o mesmo stack de tecnologia que já utilizamos" não é negociável, mesmo trocando completamente o design. Manter `react-router-dom` e um client HTTP próprio em vez de `TanStack Router`/`TanStack Query` evita que o projeto passe a ter dois paradigmas de roteamento e de busca de dados coexistindo entre `frontend/` e `frontend-v2/` durante a migração, e evita que o mantenedor precise aprender/operar um ecossistema de aplicação novo (routing + data-fetching + SSR) só porque o template de origem usa esse ecossistema — o ganho de design não depende disso. Como efeito colateral, isso também resolve a questão de SSR: sem TanStack Start, não há runtime Node em produção a gerenciar, compatível com o deploy atual (`frontend/Dockerfile`/`frontend/nginx.conf`, sem runtime Node residente, atrás do Caddy já existente em `deploy/Caddyfile`) — o produto é uma ferramenta self-hosted autenticada, sem necessidade de SEO que justificasse SSR de qualquer forma.
**Alternativa considerada**: manter `TanStack Router`/`TanStack Query` (e opcionalmente SSR) do template, por serem bibliotecas modernas e já estarem instaladas. Rejeitada por instrução explícita do usuário — a estratégia desta migração é "mesma stack de aplicação, design novo", não "stack e design novos"; trocar roteamento e data-fetching não é necessário para adotar o visual do template e teria custo de aprendizado/operação sem benefício correspondente.

### 2. bun → npm
**Decisão**: `frontend-v2/` builda com `npm` (via `package-lock.json`), não `bun`.
**Por quê**: `frontend/Dockerfile` já usa `node:22-alpine` + `npm ci`; manter o mesmo gerenciador evita duplicar ferramenta de build/CI para dois frontends dentro do mesmo repositório, alinhado com a Constitution do projeto ("reutilizar padrões existentes e justificar dependências novas").
**Alternativa considerada**: manter bun (mais rápido). Rejeitada — o ganho de velocidade de build não paga o custo de manter duas cadeias de ferramentas (lockfile, imagem base, cache de CI) para o mesmo tipo de artefato (SPA estático).

### 3. Conteúdo rico: Markdown real em vez do micro-formato do template
**Decisão**: `frontend-v2/` renderiza os campos de texto longo do backend (resumo de sessão, descrição de local/evento/item) com `react-markdown` + `rehype-sanitize` (biblioteca, não componente visual — compatível com o design system do template). As referências a entidades relacionadas (locais, personagens) aparecem como chips separados abaixo/ao lado do texto, construídos com os componentes `shadcn/ui`/tokens OKLCH do próprio `paper-parchment-pages-main` (ex. `Badge`) — nunca com o componente `Chip` ou qualquer CSS do design system "Nocturne" de `frontend/` — em vez da sintaxe inline `[[loc:id|Texto]]` do template de origem. A *regra de onde a referência aparece* (ao lado do texto, não embutida) é o único elemento preservado de `frontend/`; a implementação visual é 100% nova, no vocabulário do template.
**Por quê**: o backend persiste e já trata esses campos como Markdown puro (sanitização, contrato de API, testes existentes); o micro-formato do template é uma convenção só dele, sem suporte no backend, e exigiria uma segunda camada de parsing/serialização sem necessidade. A biblioteca de parsing é reaproveitada (é infraestrutura, não design); o componente visual que exibe o resultado não é.
**Alternativa considerada**: ensinar o backend a entender `[[loc:id|Texto]]` nesses campos. Rejeitada — muda contrato de API/dados para acomodar uma escolha só de apresentação do template de origem, contra o Non-Goal de não mudar o backend.

### 9. Zero reaproveitamento visual do frontend atual
**Decisão**: nenhuma cor, token, componente, classe CSS, ou padrão de UI do design system "Nocturne" (`frontend/`) ou de `frontend-next/` é portado para `frontend-v2/`. Toda tela — inclusive as que não existem no template de origem (Painel do mestre, Linha do Tempo, Console de administração, telas de conta) — é construída estendendo o design system de `paper-parchment-pages-main` (paleta OKLCH, Tailwind v4, `shadcn/ui`/Radix, tipografia). Onde este documento ou `tasks.md` descreve um comportamento já existente em `frontend/` como referência, essa referência é só de regra de negócio/arquitetura de informação (o que a tela faz, quais dados mostra, em que ordem) — nunca do código visual usado para implementá-la.
**Por quê**: pedido explícito do usuário — a adoção do `paper-parchment-pages-main` é uma troca de identidade visual completa do produto, não uma harmonização entre dois design systems. Qualquer mistura (ex. reusar um componente `Chip`/`FormDrawer` do Nocturne "só para economizar tempo" numa tela sem equivalente no template) resultaria num produto com dois vocabulários visuais coexistindo, o que é exatamente o resultado que esta migração existe para evitar.
**Alternativa considerada**: reaproveitar componentes genéricos do Nocturne (`Button`, `Chip`, `Drawer`, etc., documentados no style guide `/__styleguide` de `frontend/`) para acelerar telas sem equivalente no template, já que `shadcn/ui` cobre menos casos de domínio específico. Rejeitada por instrução explícita do usuário — `shadcn/ui` já tem ~34 componentes instalados no template (dialog, drawer, sheet, form, table, etc.) suficientes para cobrir os mesmos padrões de UI sem misturar origem visual.

### 4. Cálculo de rota: motor real do backend
**Decisão**: a tela de Rota chama `GET /api/c/{slug}/routes/plan` (ritmo, transporte, ordenação, preferência de via, pernoites, unidade de distância), descartando o cálculo geométrico (`Math.hypot` sobre coordenadas de imagem) do template.
**Por quê**: o template nunca teve uma rede de rotas real — seu cálculo é uma aproximação visual sobre duas coordenadas de pixel; o backend já tem o motor de planejamento completo (grafo de waypoints/segmentos, escala do mapa) que `frontend/` consome hoje. Usar o motor real é a única forma de ter paridade (Requirement "Cálculo de rota usa o motor real do backend").
**Alternativa considerada**: nenhuma — manter o cálculo fake do template não é uma opção compatível com a Requirement de paridade.

### 5. Grafo de Relações: layout dinâmico calculado por algoritmo geométrico determinístico, sem lib de simulação física
**Decisão**: o grafo de Relações em `frontend-v2/` calcula a posição dos nós em runtime com um **algoritmo geométrico determinístico, escrito em TypeScript puro, sem dependência externa** — não `d3-force` nem qualquer outra lib de simulação de física para grafos —, já que o backend não persiste `x`/`y` de personagem (ao contrário de Local, que já tem posição persistida para o mapa). As fórmulas/constantes de espaçamento são concebidas do zero para o visual novo (tamanho de card, raio, gaps do design herdado do template) — **não** é reaproveitamento de código, é a mesma escolha de tecnologia (determinística, sem lib), comparada abaixo contra a alternativa de biblioteca.

**Comparação de tecnologia — determinístico vs. `d3-force`** (comparando só a tecnologia, não a implementação/visual de nenhum dos dois lados):

| | Algoritmo geométrico determinístico | `d3-force` |
|---|---|---|
| Dependência nova | Nenhuma — TypeScript puro | Nova dependência direta (mesmo já vindo transitivamente via `recharts`, importar sem declarar é frágil — quebra se o `recharts` deixar de trazê-la) |
| Estabilidade entre renders | Garantida por construção — mesma entrada sempre produz a mesma posição, não há "assentamento" de simulação | Não garantida por padrão — é uma simulação iterativa com jitter inicial aleatório; exige fixar seed e/ou pré-computar ticks para não "saltar" a cada carga (exatamente o risco que este `design.md` já registra abaixo) |
| Complexidade de implementação/manutenção | Baixa — geometria simples (raio por contagem de nós, ângulo igualmente distribuído), testável com funções puras | Maior — exige ajustar parâmetros de física (força de repulsão, distância de link, raio de colisão, nº de iterações) até o resultado parecer certo, e não há garantia formal de não-sobreposição |
| Previsibilidade de performance | O(n) direto, sem laço de convergência | Depende do nº de iterações da simulação; cresce com o nº de nós e arestas |
| Ganho visual específico de `d3-force` | — | Agrupamento mais "orgânico" por densidade de relação em grafos grandes/irregulares — mas nenhum dos dois lados (template nem `frontend/`) usa esse estilo visual hoje, então não é um requisito do design herdado |

**Por quê**: o próprio código hoje em produção (`frontend/src/components/relacoes/graphLayout.ts`) já prova, em escala real de campanha, que um algoritmo determinístico sem dependência resolve este problema — a comparação de tecnologia acima confirma que `d3-force` trocaria uma solução mais simples e sem risco de instabilidade por uma mais complexa que reintroduziria exatamente o risco de "nós saltando" que este documento já precisa mitigar. Isso não é reaproveitar a implementação de `frontend/` (as fórmulas, constantes e o estilo de anéis concêntricos daquele arquivo são do design antigo e não são portados — Decision 9 continua valendo), é reconhecer que a escolha de tecnologia (sem lib de física) já é a mais adequada, independente do visual.
**Alternativa considerada**: `d3-force` (biblioteca de simulação física). Rejeitada pela comparação acima — dependência nova, maior complexidade de ajuste, e risco de instabilidade que precisaria de mitigação extra para alcançar a mesma garantia que o algoritmo determinístico já tem de graça.
**Alternativa considerada**: persistir `x`/`y` de personagem no backend. Rejeitada — mudaria o contrato de dados do backend sem necessidade; o comportamento atual (layout calculado, arrastável só na sessão) já é suficiente para a paridade.

### 6. Mantém os 8 tipos de vínculo reais e o modo "duas vias"
**Decisão**: `frontend-v2/` implementa o modelo completo de vínculo do backend (8 tipos, recíproco ou duas vias, qualificador e direção por sentido, redação do lado desconhecido para jogador), não a simplificação de 4 "famílias" vista em `frontend-next/` nem qualquer simplificação equivalente.
**Por quê**: é uma Requirement explícita de paridade; o backend já expõe e já redige esses campos (`public/vinculos.py`), então o trabalho é só de UI, não de backend.

### 7. Plano de cutover: coexistência, não substituição imediata
**Decisão**: `frontend-v2/` é construído, revisado e testado inteiramente como um diretório novo, sem tocar `frontend/` nem `docker-compose.yml` até a última fase. Ver Migration Plan.
**Por quê**: Requirement "Migração não regride o frontend em produção antes da paridade" — o risco de uma migração completa de frontend é alto o suficiente para justificar validar antes de trocar o que está servindo produção.

### 8. `frontend-next/` é removido, não arquivado como referência
**Decisão**: ao final desta migração, `frontend-next/` é removido do repositório (não apenas descontinuado em silêncio).
**Por quê**: confirmado que não tem nenhuma integração real nem paridade suficiente para servir de referência; mantê-lo como código morto no repositório é mais confuso do que útil, e seu histórico continua disponível no git caso seja preciso consultar.
**Alternativa considerada**: mover para uma pasta de arquivo/branch. Rejeitada como complexidade desnecessária — o git já preserva o histórico sem precisar manter uma cópia viva no `main`.

### 10. Recriar o style guide (`/__styleguide`) no design system herdado
**Decisão**: `frontend-v2/` recria um equivalente a `/__styleguide` (rota só em modo dev, como hoje em `frontend/`), documentando o design system herdado do template — paleta OKLCH, tipografia, e os componentes `shadcn/ui` efetivamente usados pelo produto (não necessariamente os ~34 instalados, só os que `frontend-v2/` de fato adota).
**Por quê**: decisão do usuário — mesmo não sendo uma funcionalidade de produto, é uma ferramenta de desenvolvimento já estabelecida no projeto (documentação viva do design system, útil para manter consistência visual ao adicionar telas novas) e vale manter o equivalente na base nova.

## Risks / Trade-offs

- **Pressa em telas sem equivalente no template (Painel, Admin, Linha do Tempo) pode levar a "emprestar" um componente visual do Nocturne (`frontend/`) para ganhar tempo** → mitigado pela Decision 9 ser explícita e verificável (tarefa 11.2 inclui checagem de que nenhum CSS/componente de `frontend/`/`frontend-next/` foi copiado); qualquer padrão de UI que falte no `shadcn/ui` já instalado deve ser construído do zero no vocabulário OKLCH/Tailwind v4 do template, não importado.

- **Paridade de ~19 telas é um trabalho grande e fácil de subestimar** → mitigado pelo inventário exaustivo em `tasks.md`, organizado por tela/área, e pela Requirement de paridade ser testável tela a tela antes do cutover.
- **Remover TanStack Start/Router/Query do template e substituir por `react-router-dom`/client HTTP próprio pode exigir desacoplar componentes do template que assumem esse harness** (ex. uso de `Route.useLoaderData()`/loaders de rota, `useSearch()` do TanStack Router para estado de seleção via query params) → risco moderado, já que o próprio padrão de "estado de navegação via search params da URL" do template (confirmado no relatório de exploração) precisa ser reimplementado sobre `react-router-dom` (`useSearchParams`) em vez de simplesmente removido; mitigado fazendo essa reescrita de roteamento na Fase 1 (infraestrutura cross-cutting), antes de portar qualquer tela de domínio, para não refazer o trabalho depois.
- **Fórmulas de espaçamento/raio do algoritmo geométrico (Decision 5) podem não se ajustar bem ao tamanho de card do design herdado do template na primeira tentativa** (nós grudados ou espaçamento exagerado) → risco baixo e sem efeito de instabilidade entre renders (o algoritmo é determinístico por construção, não uma simulação que precisa "assentar"); mitigado ajustando as constantes de espaçamento durante a implementação da task 4.2, com o teste de legibilidade já previsto nessa task (campanhas de elenco pequeno e grande).
- **Dois frontends completos coexistindo no repo por um período** (`frontend/` em produção, `frontend-v2/` em desenvolvimento) aumenta a superfície de manutenção durante a migração → aceito como trade-off necessário para não regredir produção; o período de coexistência termina no cutover (última fase do Migration Plan), seguido da remoção de `frontend/` e `frontend-next/`.
- **Regra de negócio simplificada no template (vínculos, rota) pode ter sido copiada sem querer para `frontend-v2/` se a implementação partir literalmente do código do template** → mitigado pelas Decisions 3-6 acima, que devem ser verificadas explicitamente nas tasks de Relações e Rota.

## Migration Plan

1. **Fase 0 — Bootstrap**: copiar `paper-parchment-pages-main` para `frontend-v2/`; remover todo o harness de aplicação do template — SSR/Nitro, `@tanstack/react-router`, `@tanstack/react-query` (Decision 1) —, instalar `react-router-dom`/`react-i18next`/`react-markdown`/`rehype-sanitize`/`react-zoom-pan-pinch`; trocar bun por npm (Decision 2); configurar `frontend-v2/Dockerfile` no mesmo padrão de `frontend/Dockerfile`, mas **sem** adicionar o novo serviço a `docker-compose.yml` ainda (evita qualquer risco de apontar produção para código incompleto).
2. **Fase 1 — Infraestrutura cross-cutting**: client HTTP próprio contra a API real (mesmo padrão de `frontend/src/api/`, sem lib de cache de servidor), roteamento por slug com `react-router-dom` (incluindo portar o padrão de estado de seleção via query params do template para `useSearchParams`), i18n (`react-i18next`, portando os namespaces de `frontend/src/locales/`), auth real (login/convite/reset/sessão), `EditModeContext`-equivalente para Modo GM.
3. **Fase 2 — Telas de domínio**: Mapa, Relações (Decisions 5-6), Rota (Decision 4), Sessões, Linha do Tempo (3 modos + Arcos + Itens + Descoberta + sugestões por IA) — nesta ordem ou na que a implementação achar mais eficiente, sempre validando contra a Requirement de paridade tela a tela.
4. **Fase 3 — Telas públicas e administrativas**: Home, Explorar, Painel do mestre (incl. export/import/cota/módulos/gênero/capa), wizard de criação de campanha, Console super-admin, Convites admin, Conta.
5. **Fase 4 — Validação de paridade**: checklist de `tasks.md` concluído; `frontend-v2/` roda em paralelo a `frontend/` (ex. porta/subdomínio de staging) para validação manual lado a lado.
6. **Fase 5 — Cutover**: trocar `build.context` do serviço `web` em `docker-compose.yml` de `./frontend` para `./frontend-v2`; deploy.
7. **Fase 6 — Limpeza**: remover `frontend/` e `frontend-next/` do repositório depois do cutover validado em produção.

**Rollback**: até a Fase 5, não há nada para reverter em produção (`frontend/` nunca foi tocado). Depois do cutover (Fase 5), rollback é trocar `build.context` de volta para `./frontend` e re-deploy — possível enquanto `frontend/` não tiver sido removido (Fase 6 só deve ocorrer depois de um período de confiança em produção).
