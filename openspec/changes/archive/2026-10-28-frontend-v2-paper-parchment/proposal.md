# Proposal

## Why

O usuário decidiu adotar uma base visual nova para o produto: `paper-parchment-pages-main` (projeto externo, template Lovable/TanStack Start). Não é um template genérico — seu próprio mock de dados já se chama "Campaign Codex" e modela quase 1:1 as telas centrais do produto (mapa, relações, rotas, sessões, linha do tempo), com um design system (Tailwind v4 + shadcn/ui + paleta OKLCH) que vale adotar como a nova cara do produto. Hoje esse projeto está 100% desconectado de qualquer backend (dados mockados, zero chamada de rede) e simplifica regras de negócio reais (grafo de relações com posições fixas, cálculo de rota geométrico fake, formato de texto rico incompatível com o Markdown já persistido no backend).

Ao mesmo tempo, `frontend-next/` — a segunda versão que já estava em migração neste repositório — nunca teve integração real com a API e está incompleta mesmo como protótipo (falta a Linha do Tempo inteira, Sessões é só leitura, Modo GM é um toggle local sem autenticação, Relações simplificada para 4 "famílias" em vez dos 8 tipos reais de vínculo, console de admin explicitamente marcado no próprio código como "ilustrativo, não representa o produto real"). Não é a base certa para continuar.

Esta proposta documenta a migração completa do frontend de produção para uma base nova (`frontend-v2/`), adotando o design de `paper-parchment-pages-main` mas conectada de verdade à API já existente, com paridade funcional confirmada tela a tela contra o que `frontend/` entrega hoje.

## What Changes

- Novo diretório `frontend-v2/` na raiz do repo. **Do `paper-parchment-pages-main` é adotado só o design visual** (Tailwind v4, shadcn/ui/Radix, paleta OKLCH, tipografia) — **a stack de tecnologia de aplicação continua sendo a mesma que `frontend/` já usa hoje**: React 19 + Vite + TypeScript, `react-router-dom` (não `@tanstack/react-router`), client HTTP próprio + hooks (não `@tanstack/react-query`), `react-i18next`, `react-markdown` + `rehype-sanitize`, `react-zoom-pan-pinch` para pan/zoom do mapa, e `npm` como gerenciador de pacotes. "Manter o mesmo stack" e "zero reaproveitamento visual do frontend atual" são as duas faces desta decisão: a tecnologia de aplicação (roteamento, busca de dados, i18n, renderização de Markdown, interação de mapa, build) não muda; o visual (cores, tokens, componentes, CSS) nunca vem de `frontend/`/`frontend-next/`, sempre do template.
  - **Zero reaproveitamento visual do frontend atual**: nenhuma cor, token, componente, classe CSS ou padrão de UI de `frontend/` (design system "Nocturne") ou `frontend-next/` é portado para `frontend-v2/`. Toda tela — mesmo as que não existem no template de origem — é construída estendendo o design system do `paper-parchment-pages-main` (os mesmos tokens OKLCH, a mesma biblioteca `shadcn/ui`/Radix já instalada, a mesma tipografia). Onde este documento cita um comportamento ou fluxo já existente em `frontend/` (ex. "chips de entidade ao lado do texto", "alerta de inconsistência visível só para o dono"), a referência é só à regra de negócio/arquitetura de informação a preservar — nunca ao código visual, componente ou estilo usado para implementá-la.
  - **Remoção completa do harness de aplicação do template**: `@tanstack/react-start` (SSR/Nitro), `@tanstack/react-router` e `@tanstack/react-query` não fazem parte de `frontend-v2/` — nenhum deles resolve um problema que o projeto já não resolva com `react-router-dom`/client HTTP próprio, e manter dois roteadores/duas formas de buscar dados entre `frontend/` e `frontend-v2/` custaria mais do que vale. Build como **SPA estático** (Vite puro) — consequência natural de não usar TanStack Start — compatível com o deploy atual, sem runtime Node em produção (`frontend/Dockerfile` é `node:22-alpine` build → `nginx:1.27-alpine` serve).
  - **npm** em vez de bun no build/Docker, para não introduzir um segundo gerenciador de pacotes sem necessidade.
  - **Dados reais**: substitui o mock estático (`src/lib/codex-data.ts`) por um client HTTP contra a API FastAPI já existente, no mesmo padrão de `frontend/src/api/` (client próprio + hooks), sem introduzir uma lib de cache de servidor nova.
  - **Roteamento multi-campanha por slug** (`/c/:slug/...` via `react-router-dom`), autenticação real (login, convite, reset, sessão por cookie) e Modo GM real (`canEdit`/`isDono` via `/api/c/{slug}/admin/session`) — o template só tem rotas de uma campanha fixa e um toggle visual de "Mestre" sem lógica.
  - **i18n pt-BR/en** via `react-i18next`, mesmo padrão já usado em `frontend/src/i18n/` — o template não tem nenhuma infraestrutura de idiomas.
  - **Paridade funcional completa** com `frontend/`: todas as ~19 telas/fluxos de `frontend/` são recriadas em `frontend-v2/` com o design herdado do template, mesmo quando o template não tinha telas equivalentes (Linha do Tempo nos 3 modos, CRUD completo de Sessões/Eventos/Arcos/Itens, sugestões por IA, Painel do mestre com export/import/cota/módulos, fluxos de conta, console de super-admin, etc. — inventário completo em `tasks.md`).
  - Correções de regra de negócio e de stack necessárias para a paridade: grafo de Relações com os 8 tipos reais de vínculo (não as 4 "famílias" do template) com direção/qualificador por sentido; cálculo de rota via `GET /api/c/{slug}/routes/plan` (não a geometria aproximada do template); conteúdo de sessões/eventos renderizado como Markdown sanitizado (`react-markdown` + `rehype-sanitize`, padrão já usado em `frontend/`) em vez do micro-formato `[[loc:id|Texto]]` do template; pan/zoom do mapa via `react-zoom-pan-pinch` (já usado em `frontend/`) no lugar do pan/zoom caseiro (`onPointerDown/Move/Up`/`onWheel` manual) do `WorldMap.tsx` do template.
- `frontend/` continua em produção sem alteração de comportamento até `frontend-v2/` atingir paridade e ser validado — o cutover de deploy (troca do `build.context` do serviço `web` em `docker-compose.yml`) é a última etapa desta migração, não a primeira.
- `frontend-next/` é aposentado ao final desta migração — nunca teve integração real nem paridade suficiente para justificar continuar como base.
- **Sem nenhuma mudança no backend**: toda a superfície de API já existente é consumida como está. Uma lacuna real de endpoint descoberta durante a implementação abre uma change OpenSpec própria, não é resolvida dentro desta.

## Capabilities

### New Capabilities
- `frontend-v2`: a interface web do produto passa a ser entregue a partir de uma base de código nova (`frontend-v2/`, derivada de `paper-parchment-pages-main`), com paridade funcional obrigatória em relação ao frontend atual, dados reais da API (nunca mock), autenticação/Modo GM reais, isolamento multi-tenant por campanha (rota por slug), i18n pt-BR/en, e build/deploy compatíveis com o padrão já usado pelo projeto (SPA + nginx + Docker + npm).

### Modified Capabilities
(nenhuma — `entrada-campanha`, `linha-tempo-por-arcos`, `linha-tempo-por-descoberta`, `motor-ia-arcos`, `motor-ia-evento-associacoes`, `motor-ia-sessao-associacoes` e `ia-provider` continuam valendo exatamente como já especificadas; `frontend-v2` passa a ser outra superfície que precisa continuar satisfazendo esses requirements, mas o texto deles não muda nesta proposta.)

## Impact

- **Frontend**: novo diretório `frontend-v2/` (ao lado de `frontend/` e `frontend-next/`), ~19 telas/rotas a recriar ou adaptar, client HTTP novo contra toda a API do backend, infraestrutura de i18n e de auth/sessão novas.
- **Backend**: nenhuma mudança de contrato. Dependências reaproveitadas sem alteração: `GET /api/c/{slug}/config`, CRUD de locais/npcs/personagens/vínculos/arcos/sessões/eventos/itens/waypoints/route-segments/grupo, `GET /api/c/{slug}/routes/plan`, upload e mídia, `/api/auth/*`, `/api/campanhas/*`, `/api/admin/*`.
- **Deploy**: `docker-compose.yml` ganha, só ao final da migração, a troca do `build.context` do serviço `web` de `./frontend` para `./frontend-v2`; `frontend-v2/Dockerfile` segue o mesmo padrão multi-stage de `frontend/Dockerfile`.
- **Dados/migrações**: nenhuma.
- **Descontinuação**: `frontend-next/` deixa de ser mantido; `frontend/` só é removido depois que `frontend-v2/` estiver validado em produção.
